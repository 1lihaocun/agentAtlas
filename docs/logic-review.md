## 本次已修复的运行故障

用户实际打开 `http://127.0.0.1:7788/`，该服务启动于 09:43，`GET /api/file-guide` 返回 `404 {"ok":false,"error":"unknown endpoint"}`；此前验收的独立 7790 返回 200。

根因：`atlas/serve.py:479` 每次请求读取磁盘静态页面，Python 后端却只在进程启动时导入。新增前端按钮可立即出现在旧后端上。此前只验证 7790，没有验证用户实际入口，是交付遗漏。

处理：经用户允许重启 7788，回读接口 200；在 7788 进行真实浏览器验收。停掉本会话启动的 7790，避免两个进程使用相同 `.agentatlas/` 却保留不同内存清单。前端保留 HTTP status，对缺失接口提示当前地址与重启后端，而非只显示未知端点并要求重复重试。未刷新用户现有页面或清除草稿。

**上述修复不等于实现了热重载、跨进程任务锁或版本握手。** 后端代码更新仍需重启。操作说明见 README 的“更新代码与排查接口不可用”。

## 初次审查：6 个行为缺陷

以下场景由父代理使用隔离 scratch 文件和实际 inline JS 的 Node harness 独立复现，不是仅采纳子代理报告，也不表示这些合成文件在用户真实目录中存在。

### 1. 普通 Markdown 被误判为配置

- 位置：`atlas/catalog.py:201–202`；后续记忆与命令规则在 `:211–216`。
- 复现：`.claude/commands/settings.md` 与 `.claude/projects/fixture/memory/config.md` 都得到 `category=config, editable=false`；相邻 `topic.md` 得到 `category=memory, editable=true`。
- 影响：命令/记忆筛选遗漏、记忆目录漏项、错误只读，类型说明随错误类别传播。
- 原因：优先使用裸文件 stem 判配置，没有同时约束位置和格式。
- 修复方向：明确平台配置位置与格式，不让普通主题名抢占目录用途。调整类别时仍保留配置内容检查与编辑安全约束，不能通过跳过安全检查修复分类。

### 2. 项目身份依赖扫描顺序

- 位置：`atlas/catalog.py:305–319,422–425`；指令扫描输出排序在 `atlas/scan.py:234`。
- 复现：`repo/AGENTS.md` 先输入，两份指令都属于 `repo`；扫描器实际排序让 `repo/a/AGENTS.md` 先输入，子文件改属 `repo/a`。
- 影响：「全部文件」按项目精确筛选时，父项目漏掉子目录文件。同一组路径仅顺序不同就产生不同身份。
- 修复方向：先建立独立、确定性的项目根清单，再分配资产。不能只排序后取最浅目录，因为真实嵌套仓库应有独立身份。

### 3. 展示分组被当作项目身份，记忆项目映射失效

- 位置：`atlas/scan.py:190–196`、`atlas/asset_service.py:90–114`、`atlas/memory_scope.py:176–187`。
- 复现：`Documents/Code/standalone/AGENTS.md` 的 `proj=(Code 根目录)` 被服务排除；`Documents/Codex/repo/AGENTS.md` 让服务只提供 `Documents/Codex` 候选。
- 对照：两份按真实项目路径编码的 Claude `MEMORY.md` 经服务返回 `level=unknown`；给同一解析器明确的真实项目根后返回 `level=project`。
- 影响：合法项目不出现在适用项目选项中，记忆无法关联到正确候选项目。
- 修复方向：`root/proj/sub` 仅作地图展示，不再反推出领域上的项目路径。为候选根记录来源和未知状态，不把路径匹配说成实际加载。

### 4. 只有技能等资产的项目可能完全漏扫

- 位置：`atlas/asset_service.py:167–168`、`atlas/catalog.py:305–325`。
- 复现：项目仅有 `.claude/skills/demo/SKILL.md`，旧指令扫描返回零；服务目前传入的空 `instruction_files` 不能发现该技能。显式提供同项目 `project_roots` 后可发现。
- 影响：新增文件库的覆盖依赖项目里恰好存在旧指令扫描目标，即使重新扫描也可能无声遗漏。
- 修复方向：在已授权扫描范围内独立发现项目/资产位置，或提供显式项目根配置；不要扩大为递归扫描整个 HOME，也不要取消凭证、缓存、链接和深度保护。

### 5. 返回只恢复路由，不恢复查找上下文

- 位置：`web/index.html:1003–1023,1402–1411`。
- 复现 A：有关键词和结果的文件检索 → 指令地图 → 返回，查询变为空，结果变为 `null`。
- 复现 B：记忆视图选平台、输入本地查询并翻页 → 查看器“所在目录” → 返回，平台/查询仍为空且分页归零。
- 影响：编辑草稿虽保留，查找上下文却丢失。“返回”不是回到之前的状态。
- 修复方向：历史项保存对应视图的筛选、分页、查询及结果快照；在“所在目录”清筛选之前捕获。返回云查询时恢复已有结果，不自动重发云请求；数据已过期时明确标记。

### 6. 隐藏 worktree 后计数与列表不一致

- 位置：`web/index.html:817–819,1108–1120,1185–1212`。
- 复现：两文件 fixture 中一份 worktree；隐藏后项目列表只有一行，顶部仍写“2 文件”，且项目页无解除隐藏按钮。
- 影响：用户容易将隐藏误解为漏扫；此偏好持久化，重新进入仍受影响。
- 修复方向：同一视图的计数/字节/列表用相同筛选口径；同时标出当前显示与总量，并在根和项目页提供解除入口。

## 初次审查：2 处语义与刷新设计矛盾

### 7. 旧指令页把路径启发式说成确定的全局生效规则

- 位置：`web/index.html:850–855`、`atlas/scan.py:118–121`。
- 页面断言“对你所有项目生效，项目级文件会覆盖它们”，但扫描器只凭 HOME 相对深度分类。
- 独立 fixture：扫描配置自己列在全局指令段的 `.config/opencode/AGENTS.md` 被分到 `project`。
- 与 `CONTEXT.md` 的“存放位置不等于作用范围，加载/继承需分别核实”冲突。
- 修复方向：去掉跨工具的统一覆盖断言；清楚标为位置推定候选。已核实平台规则单独维护，未知不做生效承诺。

### 8. 文件库、地图使用独立快照，但刷新边界不可见

- 位置：`web/index.html:1507–1517,1944–1958,1967–1984`、`atlas/asset_service.py:164–173`。
- 独立 fixture：刷新资产响应移除一个指令后，`ASSETS.files.length=0`，`DATA.files.length=1`；实际只请求 `/api/assets`。
- 三类数据分开本身合理：地图是指令集合，文件库是广义资产集合，记忆语义是派生视图。问题在于用户看不到各自的新鲜度和刷新范围。
- 影响：文件库已移除的文件，旧地图仍可点击；说明接口按资产清单授权，可能返回 403。这与旧后端导致的 404 是不同问题。
- 修复方向：各清单显式展示快照时间/过期状态；用清楚的统一更新操作协调扫描与派生视图。仅调用 `loadTree()` 不足以解决旧磁盘 `atlas.json`；必须更新对应扫描产物。

## 收敛后的设计边界

1. **资产发现**：在限定扫描范围内发现文件并执行安全检查，不依赖是否存在 `AGENTS.md`。
2. **项目身份**：独立的规范路径、来源、父子/仓库关系及未知状态，不复用目录展示标签。
3. **派生视图**：全部文件、记忆、指令地图基于明确的清单版本，各自分类/过滤，不混为一套继承规则。
4. **解释与观察**：文件说明回答“设计用途”，作用域回答“有条件的适用规则”，曝光回答“观测到什么”；都不彼此冒充。
5. **导航状态**：路由、筛选、分页、查询及结果是一份可恢复的浏览状态，编辑草稿另行保护。

建议先解决 1–4 的数据发现/项目身份问题，再解决 5–6 的交互一致性，同时校正 7–8 的说明与刷新契约。不要以增加更多按钮或直接拆大文件代替这些逻辑修正。

## 第二轮：扫描与刷新开销（2026-09-23）

### 已修复

- **扫描跨轮污染重复组**：`scan.scan()` 曾把 SHA 分组保存在模块全局变量里；同进程扫描第二次会重复追加路径，已删除文件也留在组中。改为每轮局部状态，删除 HTTP fixture 中手工清空全局计数的补偿代码。回归直接连续扫描、删除一个 fixture 后再扫，不再需要调用方善后。
- **重叠目录重复遍历**：只有命中文件去重，父子 ROOTS 仍重复枚举整个子树。现在本轮记录目录已覆盖的剩余深度，只跳过覆盖足够的目录；父根先扫、子根后扫仍保留子根自己的深度预算。原有凭证、缓存、链接排除和读文件时的描述符检查不变。
- **空向量状态查询也全表探测**：`embeddedChunks` 的相关子查询对每个 chunk 查一次 vectors，已有 hash 索引未避免空集合扫描。改为向量 hash 集合驱动索引查找，在同一 WAL 快照内统计；多模型相同 hash、相同正文的多个 chunks、孤立向量的计数语义保持不变。SQLite VM 步数回归不依赖墙钟阈值。
- **一次任务完成下载两遍清单**：任务恰在首次状态回读前结束时，轮询完成分支和提交分支都会调用 `loadAssets()`。现在由状态回读报告已刷新，提交分支仅补没有发生的那次读取；约 4 MB 的清单不再重复下载，记忆派生视图也只刷新一次。
- **状态读取失败后永久停在运行中**：已知任务正在执行时，GET 偶发失败曾终止轮询、一直禁用扫描按钮。现在保留“完成情况未知”并重试状态读取，不重放 POST。截图验收还发现记忆/地图页隐藏了原状态行，已把这些视图的故障和后台任务错误展示到可见快照提示中。

回归位置：`tests/test_scan_refresh.py`、`tests/test_search_index.py`、`tests/test_frontend_refresh.py`；真实故障恢复检查为 `tests/browser_refresh.mjs`。

### 测量与限制

- 相同系统 Python、相同 `cProfile` 方法，扫描耗时 **14.157 → 10.767 秒**；目录枚举 **64,142 → 41,540 次**。对照的 180 条指令路径、SHA、项目归属、重复标记和分组完全一致，扫描错误均为 0。此数字是带分析器的单轮对照，不是完整重扫/索引耗时，也不是跨机器保证。
- 正式 7788 状态接口，旧版连续三次 **1.463 / 0.050 / 0.050 秒**，新版 **0.009 / 0.007 / 0.007 秒**；冷/热缓存差异明显，不用最慢旧样本计算倍数。另在同一只读 SQLite 事务里执行旧/新 SQL，计数一致；真实库当时未生成向量，多模型非空语义由隔离测试覆盖。
